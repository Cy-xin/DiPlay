# Geely 音频与语音可靠性 · 版本 50

## 用户报告与证据边界

用户报告 Siri、微信首次收音无效，重试两三次后恢复；CarPlay 音量可能过小或过大。本轮未连接车机，因此源码缺陷可确认，用户实际故障根因尚未实车确认。

## 本轮修改

- 输入型语音流在 SETUP 后异步启动麦克风，去掉无下行音频时额外的 500 ms 等待。仍要求 iPhone 明确请求输入；通话保留等待下行的原有时序。
- AudioRecord 每次按协商帧读取。旧版至少读取 2048 字节：16 kHz、16 位单声道相当于 64 ms；20 ms 帧为 640 字节。此处减少的是读取积累等待，不代表端到端延迟已测得降低 44 ms。
- 车辆音频路由检测已退出的录音线程，清除失效实例，在同一流中重建录音；保留原 RTP 计数。语音启动失败按 0.5、1、2、5 秒退避，通话保留 5 秒重试间隔。停止流后不再启动录音。
- 静音诊断增加系统麦克风静音及 Android 10+ 的并发录音静音状态，不自动解除系统静音，也不记录语音内容。
- 音频设置新增 CarPlay 播放音量 -18 至 +6 dB，默认 0 dB，使用 PCM 缩放并钳位，适用于 DiPlay 输出的音频，立即生效，不修改 Android/OEM 系统音量。正增益可能发生削波失真。原生蓝牙直连不经过此处理。
- 无线音乐缓冲新增 150、200 ms 可选值；默认保持 300 ms。低缓冲可能增加 Wi-Fi 波动时的断续。保留旧偏好及设备的最小 AudioTrack 缓冲下限；有线选项保持不变。

## 未做未经测量的修改

没有缩短蓝牙认证、Wi-Fi 配置、配对超时，也没有更改分辨率、帧率、音频采样率或抹掉旧设置。连接流程已有 Bluetooth connect completed elapsedMs 等阶段日志，需实车比较后定位连接耗时；运行帧率和端到端音频延迟也需实测。

Android 并发录音规则参考官方说明：
https://developer.android.com/media/platform/sharing-audio-input

## 验证

专项测试覆盖：帧长读取、录音失效可见、同一输入流恢复及停止后不重启、输入流无下行仍能启动、正负增益／范围／饱和、偏好初始化与现有播放实例即时更新、设置对话框保存、低缓冲值兼容。完整 CI 另覆盖普通构建与静态检查。界面包括宽屏、窄屏、大字体和 RTL 预览。

实车验收：

1. 冷启动 CarPlay 后首次打开 Siri，提示后正常说话；连续做三次，并测试微信录音开头是否完整。
2. 分别确认听不到声音时的麦克风状态、source、peakDbfs、clientSilenced 和录音恢复日志；若持续输出全零 PCM，需要进一步检查原车语音服务或 HAL，不把安静环境当作故障反复重启。
3. 从 0 dB 开始：过小可试 +3 dB，过大可试 -3／-6 dB；分别检查音乐、导航、Siri 和通话。若原生蓝牙直连，应使用车机音量。
4. 无线缓冲先试 200 ms，再比较 150 与默认 300 ms；有断续恢复 300 ms。记录实际端到端等待，不把配置值当作实际延迟。
5. 对比首次连接和已配对重连的阶段耗时、系统负载与界面响应。
