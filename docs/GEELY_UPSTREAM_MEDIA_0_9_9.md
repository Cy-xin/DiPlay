# 0.9.9：复用原版画面与音频处理

## 来源及范围

- 当前分支：`codex/geely-return-picture`，修改基线：`e2c54940`（0.9.8）。
- 原开源来源：`shihabal3amri/DiPlay`，固定提交 `615b32ce0b40cd0b99ce94ba23a512001553684f`。本次从 GitHub 取得该提交的源文件，未将本地已经修改过的 shared 模块冒充原版。
- 保留原仓库 GPL-3.0 许可。没有新增依赖，没有改变连接模式、页面、包名或认证资产分发方式。

## 已经复用，继续保留

`AudioStream` / `ScreenStream` 的网络接收、解密和帧传递，`VideoDecoder` 的配置、队列、解码及输出循环，`VideoDecodeQueue` / `VideoBacklogRecovery` / `VideoSurfaceHandoff`，以及 `MediaAudioBuffer` / `AudioBufferProgress` 均与固定原版对应实现相同。

可运行 `python3 scripts/verify_geely_upstream_media.py --upstream <原版源文件目录>` 核验十个范围。目录包含 `airplay/` 与 `media/`。脚本校验固定源文件摘要，只归一化文件末尾空白及 ScreenStream 构造器排版，并明确只剔除 VideoDecoder 的三个观察点及音频时钟两个只读诊断属性；输出原文件摘要。它验证选定范围的源码一致性，不证明全部应用或运行表现等价。

视频沿用原版已有的独立输出线程路径。吉利版继续选择启用该路径，因为此前实车测试确认改善；本次没有另加帧调度算法。三个观察点分别记录入队等待、通知已显示帧以及传递当前解码器/Surface，用于已交付的画面恢复判断。

## 本次恢复的原版逻辑

- `MediaClockTrim` 恢复原版的缓冲时间平均、稳定阶段目标测量、PI 时钟校正与校正频率。仅增加读取目标和校准状态的诊断属性。
- `AudioRenderer.trimClock` 恢复原版调用：只在写入 PCM 后采样；计算包含压缩队列和包到达时间的缓冲量，丢包后重新校准，系统拒绝速率调整则退出校正。
- 移除本地额外的测量目标上限、低 PCM 特殊制动及两次写入之间的额外速率调整。原版已有的队列限制、丢旧包、欠载重缓冲及解码机制保留。
- 日志标记 `clockModel=upstream`，不再输出已移除的保护计数。

这是按用户要求回归上游策略，并不声称旧策略已被证明是卡顿根因。原版时钟策略可能测得高于启动阈值的稳定缓冲目标；不能把配置的启动缓冲直接当成端到端延迟。真实无线传输中断仍可能造成重缓冲。

## 必须保留的本地适配

- 吉利媒体、导航、通话、助手音频通道及可配置映射；导航渐弱/恢复和音量滚轮提示；蓝牙音乐交接。
- 已验证的 Siri 麦克风输入、Opus 软件兼容路径。
- 后台连接存活、Surface 安全交接及画面恢复失败反馈。
- `MediaPacketLagGuard` 追平后立即结束拥塞恢复的局部修复。
- 采样快照后到达的包不计入过去时间积分，避免并发到达导致负时间；已有对应回归测试。

直接整体替换媒体外壳会覆盖这些适配，因此只恢复原版控制算法及相应调用，不重新引入原版其他车型功能或服务。

## 验证方法

1. 固定来源的源码对比（十个范围）。
2. 原版音频时钟单元测试，加突发流、阻塞写入校准测试。
3. 测试专用原版参考实现（只改类名），分别在校准/固定目标模式下，对三种初始漂移、音频突发、低 PCM、压缩积压、长间隔和重新校准逐次比对输出速率及学习值。
4. 维护循环不额外调整速率、系统拒绝调整后继续播放，以及导航混音、Siri 和画面交接等现有回归检查。
5. 项目原有 CI、吉利模块单元测试、lint、APK 构建及包名/版本/认证输入/签名检查。

旧测试里专门验证额外制动、目标上限的断言已按新的上游行为替换，而非继续保留互相矛盾的要求。导航渐弱测试保持原有覆盖；移出其中与导航无关的时钟上限测试。

离线通过不代表实车流畅度或断音问题已经解决。仍需车机复测音乐与导航混合、切换应用、后台返回、Siri、长时间播放及网络短暂中断。
